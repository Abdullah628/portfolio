# Tainc CRM — Entire Features List

A complete catalog of every feature in the platform, derived from the backend module set
(`tainc-backend/src/app/modules`, ~180 modules), the seeded feature catalog
(`modules/seeder/data/fullFeatureCatalog.json`, 68 top-level features / ~180 sub-features),
the route table (`src/app/routes/index.ts`, ~150 mounted route groups), and the frontend
screens (`tainc-frontend/src/pages`, ~110 admin page groups).

**Stack:** Express 5 + TypeScript + Mongoose (MongoDB), Zod validation, Socket.IO, node-cron,
Puppeteer (PDF), Stripe, Twilio, VAPI, Anthropic/OpenAI SDKs, SendGrid/Mailgun/SMTP —
frontend React 19 + Vite + Redux Toolkit + Tailwind + Radix + FullCalendar + Google Maps.

**Domain:** a multi-tenant SaaS CRM built for field-service/tree-care companies, resold
white-label through agencies.

## 1. Platform Architecture & Tenancy

The platform is a **four-layer tenant hierarchy**, declared as `TENANT_LAYERS` in
`modules/feature/feature.interface.ts`:

```
SUPER_ADMIN  →  AGENCY  →  ORGANIZATION  →  CLIENT
 (platform)     (reseller)  (paying business)  (the org's customers)
```

| Layer            | What it owns                                                                                                                    |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| **SUPER_ADMIN**  | The global feature catalog, feature groups, platform settings, agency plans. Sells platform subscriptions to agencies.          |
| **AGENCY**       | White-label reseller. Owns CRM plans, its own service/package catalog, lead packages, onboarding templates, and bills its orgs. |
| **ORGANIZATION** | The subscribing business — the actual CRM tenant. All operational data lives here.                                              |
| **CLIENT**       | The org's own customers, in a restricted portal.                                                                                |

Alongside the layer axis, two more orthogonal axes govern visibility:

- **Audience** (`internal` / `external` / `admin`) — which org-tier menu a screen belongs to
  (employee-facing / job-facing / back-office). Carried on both features and sub-features,
  because `production` and `operations` each span all three.
- **Role** — what a person may actually do, via action grants.

System roles: `SUPER_ADMIN`, `AGENCY_ADMIN`, `SUPPORT_AGENT`, `ADMIN`, `ORG_ADMIN`, `MANAGER`,
`TEAM`, `HR`, `SUPPORT`, `PROJECT_MANAGER`, `CREW`, `CLIENT` — plus fully dynamic custom roles
per org.

**Multi-account identity** — one email address can hold accounts across several orgs/agencies;
login, password reset and OTP delivery all resolve which tenant is being acted on.

## 2. Access Control, Plans & Feature Gating

| Feature                              | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Feature Catalog**                  | SUPER_ADMIN-owned global two-level tree (features → sub-features) of every capability in the platform, each with per-role action grants. Also carries all navigation metadata (group, route, icon, sort order, nav label, tenant layers), which is what makes the sidebar database-generated rather than shipped in a build. Supports catalog export/import, duplicate-key detection, and a dependency report — dependencies are _reported_, never auto-granted. |
| **Feature Types**                    | `commercial` features are paywalled by plan; `system` features (dashboards, settings, profile, administration) are mandatory platform capabilities that plans neither grant nor withhold.                                                                                                                                                                                                                                                                        |
| **Feature Groups**                   | The collapsible sidebar sections features render under. Groups hold no permission — a group renders only when at least one feature inside it survives permission resolution, and vanishes when none do. Supports nesting, per-layer and per-audience visibility, and exactly one fallback catch-all group.                                                                                                                                                       |
| **Feature Restrictions (deny-list)** | The single storage table behind the whole permission model. Everything in the Super Admin catalog flows down to every layer; a layer may only _subtract_. Denies accumulate at five scopes — `ROLE_DEFAULT → PLAN → ORG → ROLE → USER` — and a lower layer can never re-grant what a higher one denied. Empty `denyActions` denies the whole node and its children. Includes an `/explain` endpoint for tracing why a permission resolved as it did.             |
| **Plans**                            | Agency-authored subscription plans an org buys for CRM access: duration (day/week/month/year × value), base price, bundled services and packages, trial support with auto-conversion to a post-trial plan. `featureMode: ALL_EXCEPT` (default) stores a _denylist_ and renders the grant list as compiled output, so a feature added to the catalog tomorrow flows into existing plans automatically.                                                            |
| **Org Feature Policy**               | Per-organization overrides of the role→action grant table, at both feature and sub-feature level, distinguishing plan-written from manually-set entries. Being superseded by the deny-list model.                                                                                                                                                                                                                                                                |
| **Dynamic Navigation**               | `GET /navigation/me` serves each user their own sidebar, derived entirely from their resolved access — no role gate needed. Resolves the caller's tenant layer, intersects user feature access with the org plan, and assembles groups/features through a pure resolver.                                                                                                                                                                                         |
| **Role Envelopes**                   | Platform-wide ceilings per role that keep inheritance inside its tier, with bounded portal surfaces (`CLIENT_PORTAL_PATHS`, `CREW_PORTAL_PATHS`).                                                                                                                                                                                                                                                                                                                |
| **Platform Settings**                | Global OpsROI white-label branding: company name, logo, colors, gradient angle, signup page copy, platform timezone. `GET` is deliberately public so pre-auth pages render correctly.                                                                                                                                                                                                                                                                            |
| **Seeder**                           | One SUPER_ADMIN endpoint running ~35 named operations — full system bootstrap, feature catalog seeding, navigation catalog seeding, role settlement, plan migration, restriction migration, email template refresh, index migrations, one-time data fixes. Most destructive ops default to `dryRun: true`.                                                                                                                                                       |

Manages the `TaincAgencyPlan` catalog (base price covering N included orgs, plus a per-extra-org overage price) and drives seat reconciliation — a cron counts active orgs and charges the agency's saved card, writing an `AgencyBillingTransaction` per charge. This ledger survives agency deletion.                                |
| **Agency Meetings**                  | Scheduled agency↔org meetings (online/phone/in-person) rendering a shared calendar, with a request/negotiation layer: either side proposes a time, the responder approves, rejects, or counters with an alternative, and the initiator confirms.                                                                                                         |

Freezes a `metricsSnapshot` of what the model saw so reports stay auditable, records model/prompt-version/token counts, and moves DRAFT → PUBLISHED. Orgs can request reports with a threaded comment log. |
| **Agency Vault Requests**            | Bidirectional secure asks between agency and org (documents or credentials), in either direction, with the response stored on the request record and passwords AES-encrypted.                                                                                                                                                                            |

## 6. Sales — Leads, Pipelines & Opportunities

| Feature                       | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                          |

| **Pipeline Analytics**        | Conversion rate, lost/converted counts, average time per stage.                                                                                                                                                                                                                                                                                                                                                                                                      |
| **Contacts**                  | The org's address book, separate from leads and client accounts: name, email, phone, profile URL, type, tags, timezone, structured geo location, and per-channel consent flags (DND all, email, external message, call & voice, inbound calls & SMS). | **Pending Lead Tracker**      | A spreadsheet-style tracker for inquiries not yet in the pipeline: date of inquiry, customer, work order, method of communication (Text/Email/Call/GoHighLevel/Google Lead/Walk-In/WebLead/Facebook), office admin owner, and whether it was posted to the sales chat. Operational statuses ("Waiting On Photos", "Site-Visit Required", "Waiting On CA's", "Estimate Declined"…), last-contact date, three follow-up checkboxes and a threaded note log.            |
| **Incoming Lead Report**      | A daily lead-volume counter for marketing attribution, across ~32 predefined sources (BetterLeadz, AI Receptionist, BBB, Chip Drop, Facebook, Google Lead, Nextdoor, Referral, Yelp, Walk-in, Web Chat, WVL MEDIA…), with today / weekly / yearly-monthly / grand-total report endpoints.                                                                                                                                                                            |

## 7. Estimating, Proposals & E-Signature

| Feature                             | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Estimation Builder**              | A rich estimate on every lead: service lines, crew lines by user category, vehicle/equipment lines and packages — each with hours × hourly rate, quantity, computed subtotals, and per-line **billable / visible / inclusion** flags where inclusion is `included`, `recommended` or `optional`. Rolls up to a profit margin and grand total.                                                                                                                                                                                                                              |
| **Service Catalog**                 | The org's atomic quoting unit: name, description, hourly rate, hours, computed total cost and optional named sub-tasks. Used by estimates, jobs, packages, fulfillment packages and map trees; a default set is bootstrapped per org.                                                                                                                                                                                                                                                                                                                                      |
| **Packages**                        | Reusable service bundles for quoting — named items (catalog service or fully custom) each with hours per unit, rate, quantity and subtotal, rolling up to package total cost and hours.                                                                                                                                                                                                                                                                                                                                                                                    |
| **Fulfillment Packages**            | Pre-built "how we deliver this job" loadouts combining service items, crew lines by user category and vehicle/equipment lines with rates, quantities, hours and billable flags. Applied on the map (expanded onto a tree) and in job estimation so a full crew-and-equipment set drops in with one click.                                                                                                                                                                                                                                                                  |
| **AI Estimation Assistant**         | A private chat session per lead per estimator. The estimator describes the site in text and photos; the model asks follow-ups until a four-item checklist is satisfied (service needed, trees/area, equipment, crew), then proposes draft line items chosen **only from the org's own catalogs**, each with quantity, hours and a stated reason, plus an "unmatched" list. The AI never prices — every rate is copied from the database row at resolution time. Once `readyToBuild`, the draft hands straight to the estimation editor. Provider/model recorded for audit. |
| **DocSign (E-Signature)**           | In-house proposal and signature engine. Documents move DRAFT → SENT_TO_SENDER → SIGNED_BY_SENDER → SENT_TO_RECEIVER → SIGNED_BY_RECEIVER → COMPLETED (or REJECTED), capturing signature metadata on both sides (IP, device, user agent, geolocation, timestamp) and generating a PDF.                                                                                                                                                                                                                                                                                      |
| **Interactive Proposals**           | Proposals snapshot the estimate as selectable `proposalItems` flattened across service/crew/vehicle lines with included/recommended/optional inclusion, so the client ticks optional extras on an **unauthenticated** signing page and the total is recomputed server-side (deposits re-priced proportionally).                                                                                                                                                                                                                                                            |
| **Proposal Payment & Provisioning** | Deposit or full payment collected at signing via Stripe. On completion the flow provisions the client account, creates the job, and moves pipeline stages exactly once via a completion lock. Also supports approve/reject with reason, refresh-from-lead, and update-payment-and-resend.                                                                                                                                                                                                                                                                                  |
| **Custom Placeholders**             | Org-registered merge tokens (e.g. `webhook.customer_company`) with a label, picker group and description. No value is stored — the placeholder only makes the name discoverable in Send Email/SMS field suggestions, resolving at send time through the dotted-path merge renderer against live webhook/form/lead context.                                                                                                                                                                                                                                                 |
| **Signatures (Handbook)**           | Employee handbook acknowledgement signatures — drawn or typed, stored as base64, stamped with the handbook version, signed-at and a validity flag. Admins get an org-wide roster of signed/unsigned users filterable by version.                                                                                                                                                                                                                                                                                                                                           |

## 8. Site Mapping & Tree Inventory

| **Per-Tree Billing**          | Trees carry billable service items, crew and vehicle lines expanded from fulfillment packages, photos, a note/photo timeline, multi-year service terms (1–3 years) and recurring-service dates — feeding straight into the estimate.                                                                                                                                                                                                                                         |
| **Per-Pin Map Images**        | Close-up static-map images per pin, embedded in proposal and invoice PDFs with a content-keyed disk cache.                                                                                                                                                                                                                                                                                                                                                                   |

## 9. Job Execution & Scheduling

| Feature                          | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Jobs**                         | The work-execution record created from a won lead: `jobId`, client/contact/clientType/map links, location, attachments, assignees and sales reps. Statuses run `needs_scheduled → schedule_confirmed → active → completed → pending_payment → follow_up → paid`, plus `service_call` and `success`, with a legacy status map for renamed keys.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| **Job Estimation**               | A snapshotted `leadEstimation` plus an editable `estimationCost` of service/crew/vehicle line items (hours, rates, margin, billable/visible flags, tree-sourced lines), with full CRUD on services, custom services, packages, package-services and expenses, and a cost breakdown view.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| **Scheduling**                   | Assigns crew members, vehicles and teams with calculated vs overridden estimated hours, availability checking, and calendar event generation.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **Service Calls**                | Numbered follow-up visits on a job, each with its own priced estimation snapshot, work order, crew/vehicle assignment and status.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| **Direct Job Creation**          | Creates lead + client + contact + job in a single step, bypassing the sales pipeline.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| **Job Completion Approval**      | Optional client sign-off. Staff request approval instead of completing; the job stays scheduled and entered completion hours are held on the request until approval. Two kinds — job COMPLETION (approving completes the job) and SERVICE_CALL_COMPLETION (approving moves the card to `success`). Delivered by a rate-limited tokenized public link (revocable via a stored `jti`, never storing the token) or in the authenticated client portal. The client signs by drawing or typing, or declines with a reason. Failed pipeline moves surface as `stageMoveError` rather than being silently lost.                                                                                                                                                                                                                                                                                                                                               |
| **Client Service-Call Requests** | A CLIENT raises a service-call request against one of their jobs with a reason and photos, eligible from **any** job stage (guarded against duplicate pendings rather than by stage). Approving moves the job to the `service_call` stage.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| **Route Planner**                | The dispatch and routing board. Pulls mappable stops (jobs and leads) with filters for type, assignee, date range, job status, lead stage, search and assignment state, geocoding on demand and reporting how many records had no location. A dispatch view returns the four on-site scheduling stages with real time windows, durations, and whether a slot is **customer-locked** (immovable anchor) or **dispatch-provisional**. Dispatchers assign crew singly or in bulk, schedule a stop explicitly or auto-place it after the crew's last commitment, and commit a whole optimized day via `apply-schedule` — which hard-blocks conflicts with 409 and returns warnings for after-close, before-open, missed anchor, holiday or closed-day.
